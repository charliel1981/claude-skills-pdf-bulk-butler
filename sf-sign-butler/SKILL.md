# SIGN Butler V2 skill

Native Salesforce e-signature sitting **on top of PDF Butler**. PDF Butler renders the document; SIGN Butler V2 sends it to the stakeholders and collects signatures. Two namespaces: the v2 package is `cadmus_sign2`; a legacy v1 package `cadmus_sign` may coexist in the same org (the Academy's Installed Packages screenshot shows both active) — **always target v2 explicitly** in new installs.

## When to trigger

Any of:

- User mentions **SIGN Butler**, **SIGN Butler V2**, **Sign Request**, **Sign Request Template**, **`cadmus_sign2`**, **e-signature in Salesforce** (with PDF Butler in scope).
- Request shape: "send this PDF for signature", "wire up SIGN Butler to my quote Pack", "add a signature placeholder to my Word template", "configure Sign Butler reminders", "customise the signing email".
- Troubleshooting: signing email not going out, placeholder numbering wrong, CoC not generating, expiry batch not firing, stakeholder count too high, Sign Butler tab missing.

## Dependencies

- **PDF Butler** (`cadmus_core`) managed package — **MUST be installed first**. SIGN Butler V2 reuses PDF Butler's rendering + DataSource stack.
- Same **PDF Butler tenant credentials** (username + admin password) — SIGN Butler registers via the same OAuth connection.
- Optional: **BULK Butler** (`cadmus_batch`) — combine with the `SignButler` Actionable on a Batch Info when sending many Sign Requests at once.
- Optional: **Collaboration Butler** (`cadmus_una`) — for SharePoint delivery of signed + CoC PDFs.

## The mental model

```
PDF Butler Pack
  ├── DocConfig (Main Word PDF with SIGN_PLACEHOLDER / INITIAL_PLACEHOLDER ConfigTypes)
  │     └── renders the document with numbered signature placeholders
  └── Actionable (Record Type = "Sign Butler", When = AFTER)
        Class = cadmus_sign2.Actionable_SignButlerSilent   (emails the signer)
            OR  cadmus_sign2.Actionable_SignButlerSignNow  (redirects in-page, no email)
        Sign Request Template = <lookup>
              └── defines stakeholders, signing methods, emails, expiry, branding
```

Everything below wires that pattern.

## Post-install setup (from the [Configuration Sign Butler V2.pdf](https://assets.pdfbutler.com/website/academy.folders/Configuration%20Sign%20Butler%20V2.pdf) referenced by the Academy — 14-page authoritative guide)

Prerequisites (before SIGN Butler itself):

1. A working PDF Butler **DocConfig** for the document to be signed (a standard Main Word PDF DocConfig). See the sf-pdf-butler skill.
2. **Signature placeholder image** pasted into that DocConfig's Word template. Download "Signature Placeholders" ZIP from Academy (referenced on the Complete Guide page; exact URL not exposed in prose).
3. A **DataSource** returning stakeholders. Academy's verbatim sample SOQL:

   ```sql
   SELECT OpportunityId, Contact.FirstName, Contact.LastName, Contact.Email, Contact.Id
   FROM OpportunityContactRole
   WHERE OpportunityId = :recordId
   ```

Then, in order:

1. **Enable Folders and Enhanced Sharing** — Setup → Email → Lightning Email Templates.
2. **Install SIGN Butler V2** — AppExchange: [listing `a0N3A00000G0oZxUAJ`](https://appexchange.salesforce.com/appxListingDetail?listingId=a0N3A00000G0oZxUAJ).
3. **Assign a permission set** to each user — either `SIGN Butler Admin` or `SIGN Butler User` (exact verbatim labels).
4. **Assign a SIGN Butler License** — Setup → Installed Packages → SIGN Butler → Manage Licenses.
5. **Register** — SIGN Butler App → **Admin** tab → enter **PDF Butler Username** + **PDF Butler Admin password** → click **Check credentials**. OAuth consent titled "SIGN Butler Connected" requests "Access your basic information / Access and manage your data / Perform requests on your behalf at any time". Success message: `SIGNV2 Butler is now connected to your org : https://pdfbutler.my.salesforce.com with user pdfbutler_partner`.
6. **Set Deliverability Access level to "All email"** — Setup → Deliverability → "Access level" = "All email".
7. **Create a lookup on `Sign Request` to the master object** — e.g. an Opportunity lookup with label "Opportunity", API name `Opportunity__c`, Child Relationship Name `Sign_requests`. Academy: "By default, we provide with a lookup field to the Account object, so if you are going to be generating the document from the Account object, you can skip this step."
8. **Create a Sign Request Template** — SIGN Butler App → **Sign request templates** tab → **New**. (Full field list below.)
9. **Create a PDF Butler Pack + Actionable** — App Menu → PDF Butler Packs → New → set Leading Doc Config → on Actionables related list → **New → Sign Butler record type** → configure:
   - `Actionable Name` — free text
   - `Class` — `cadmus_sign2.Actionable_SignButlerSilent` (email signer) or `cadmus_sign2.Actionable_SignButlerSignNow` (redirect in-page, no email)
   - `When` — **always** `AFTER`
   - `Active` — must be checked
   - `Pack` — the Pack just created
   - `Sign Request Template` — the template just created
10. **Tag the Word template** with signature placeholders — each placeholder box carries an auto-incremented number (the PDF Butler `SIGN_PLACEHOLDER` ConfigType drives this).
11. **Add the Previewer to the record page** — PDF Butler Document Previewer component (`LC_PreviewComponent`) on the record's Lightning page. Attribute set (labels verbatim): `DocConfig to retrieve`, `packs to retrieve`, `Run the DocConfigs of the Pack`, `deliverytype Overwrite` (values include `NONE`), `Locale required?`, `API name of the field to use as locale.`, `Currency locale required?`, `API name of the field to use as currency locale.`, `Alternatives enabled?`.
12. **Test** — click the PDF button on the Previewer → review → click **Sign Pack** → document forwards to stakeholders.

**Important**: share the `SignButlerEmails` email template folder with all users using SIGN Butler (Academy: "Make sure the sharing is done on this folder for all users using SIGN Butler!").

## PDF Butler side: `SIGN_PLACEHOLDER` / `INITIAL_PLACEHOLDER` ConfigTypes

Lives on `cadmus_core`, not `cadmus_sign2` — these are PDF Butler ConfigTypes configured on the DocConfig that will be signed. See also `reference/configtypes.md` in the sf-pdf-butler skill.

| Behaviour | Detail (Academy verbatim) |
|---|---|
| Auto-counter | The placeholder number auto-increments across multiple signers (1, 2, 3, …) when looped over a LIST DataSource of stakeholders |
| Numbering reset | "If you want to re-start the numbering from 1, use `-1` here." |
| Size options | "100%, 75%, 50% or 25%" |
| Data source shape | LIST DataSource supported for loop processing |
| Sibling | `INITIAL_PLACEHOLDER` — same mechanics, for initials rather than full signatures |

**Exact `cadmus_core__ConfigType__c` field API names backing SIGN_PLACEHOLDER (counter field, size field, reset-value field) are not published on the Academy — verify in-org if building metadata programmatically.**

_Source: [SIGN_PLACEHOLDER ConfigType with PDF Butler](https://www.pdfbutler.com/academy/sign-butler-academy/sign-butler-v2/sign-butler-v2-sign_placeholder-configtype-with-pdf-butler/)._

## Custom email merge tokens

Use these in your branded SIGN Butler Lightning Email Templates. All verbatim from the [Custom emails page](https://www.pdfbutler.com/academy/sign-butler-academy/sign-butler-v2/sign-butler-v2-custom-emails-with-extra-email-fields/):

**Sender tokens**:

- `[[!SignButler.Sender.Name!]]`
- `[[!SignButler.Sender.FirstName!]]`
- `[[!SignButler.Sender.LastName!]]`
- `[[!SignButler.Sender.Email!]]`
- `[[!SignButler.Sender.Title!]]`

**Recipient tokens**:

- `[[!SignButler.Recipient.FirstName!]]`
- `[[!SignButler.Recipient.LastName!]]`
- `[[!SignButler.Recipient.Email!]]`

**Request-level tokens**:

- `[[!SignButler.SignURL!]]` — unique signing URL for this stakeholder
- `[[!SignButler.DownloadURL!]]` — download link for the signed bundle
- `[[!SignButler.MailOTP!]]` — OTP when mail-OTP authentication is used
- `[[!SignButler.RejectionReason!]]` — populated on rejection notifications
- `[[!SignButler.SignRequestName!]]` — the name derived from the "master object field for sign request name"

**Extra tokens**: populate via the Sign Request Template's `extra email merge fields datasource`. Schema for that DataSource is not published — typically a KEYVALUE. Verify in-org.

Standard Lightning email merge syntax (`{{{Recipient.FirstName}}}`) also works alongside the `[[!SignButler.*!]]` tokens.

## Expiry, Reminder, and Expiration batch jobs

Three scheduled Apex batch jobs drive the reminder / warning / expiration emails. Configured from **SIGN Butler App → Admin tab → Batch Jobs → NOTIFY Batch Job** (label verbatim) via a **CRON Expression** input.

**Two expiration modes** (verbatim from the [Expiry overview page](https://www.pdfbutler.com/academy/sign-butler-academy/sign-butler-v2/sign-butler-v2-expiry-overview/)):

- `Fixed end date approach` — a single expiry date set on the Sign Request
- `DataSource and Date Field approach` — expiry resolved per-record from a DataSource field

**Configurable labels** (verbatim — mirrors the Sign Request Template):

| Field | Example (Academy) |
|---|---|
| `Number of days to wait before reminders` | 10 days |
| `Frequency of reminders in days` | every 5 days |
| `Number of days before expiration` | 30 days |
| `Number of days before expiration warning` | — |

**Choose OWA for batch jobs** section — three options (verbatim):

- Static OWA
- OWA per User
- Batch OWA

**Choose Reply-To strategy for batch jobs** — two values (verbatim, all-caps):

- `SIGN_REQUEST_OWNER`
- `MASTER_RECORD_OWNER`

**Example cron timings** (Academy): "jobs running daily at 7AM, 6AM, and 5AM respectively" (one cron per batch role — reminder / warning / expiry).

**Apex class names for the three batch jobs are not published on the Academy** — check Setup → Apex Jobs after a first scheduled run, or Setup → Apex Classes filtered by namespace `cadmus_sign2`.

## VisualForce as the document to sign

Alternative to a PDF-Butler-generated DOCX — render a Visualforce page as PDF and use it as the document being signed.

_Source: [Use VisualForce page as PDF document to sign](https://www.pdfbutler.com/academy/sign-butler-academy/sign-butler-v2/sign-butler-v2-use-visualforce-page-as-pdf-document-to-sign/)._

Static Resource name (verbatim): `SIG001TOSIG010`. The Academy shows `SIG001.png` and `SIG002.png` inside it — implying up to 10 placeholders (`SIG001`…`SIG010`), but only two are confirmed in writing. Verify the full asset list in the shipped Static Resource.

Verbatim sample:

```apex
<apex:page showChat="false" showHeader="false" applyBodyTag="false"
    applyHtmlTag="false" renderAs="PDF">
  <html>
    <body>
      <table width="100%">
        <tr>
          <td width="50%">Signer 1</td>
          <td width="50%">Signer 2</td>
        </tr>
        <tr>
          <td><apex:image
                url="{!URLFOR($Resource.SIG001TOSIG010, 'SIG001.png')}"
                alt="SIG001"/></td>
          <td><apex:image
                url="{!URLFOR($Resource.SIG001TOSIG010, 'SIG002.png')}"
                alt="SIG002"/></td>
        </tr>
      </table>
    </body>
  </html>
</apex:page>
```

Each `SIG00N.png` placeholder hydrates into a signature slot at runtime (matching the same auto-counter mechanic as `SIGN_PLACEHOLDER`).

## Common failure modes

| Symptom | Likely cause | Fix |
|---|---|---|
| "Check credentials" fails | Wrong PDF Butler admin password, or PDF Butler not registered in the same org | Verify PDF Butler registration first (see sf-pdf-butler skill); use the ADMIN password from the registration email |
| Signing email never arrives | `Actionable Class` set to `Actionable_SignButlerSilent` (correct for email flow) but SignButlerEmails folder not shared with the running user | Share the `SignButlerEmails` email template folder per Academy guidance |
| Signing opens a redirect the user didn't expect | `Actionable_SignButlerSignNow` was used — it redirects in-page and **does not** send an email | Switch to `Actionable_SignButlerSilent` for email-based flow |
| Placeholder numbers restart unexpectedly | `-1` reset value present where it shouldn't be, or placeholders are nested in more than one LIST DataSource loop | Audit the SIGN_PLACEHOLDER `reset` config; keep the loop source LIST DataSource single-level |
| Sign request expired but no warning email sent | NOTIFY Batch Job cron never scheduled, or `Number of day before expiration warning` unset | Admin tab → Batch Jobs → set CRON Expression; set all four expiry numeric fields on the template |
| CoC is missing after signing | CoC toggle not enabled on the template, OR running licence does not include CoC — Academy: "if you have no license, the CoC will be ignored" | Confirm licence with PDF Butler Support; enable toggle on Sign Request Template |
| CoC rejected with "too many signers" | CoC caps at 7 signers — Academy verbatim | Reduce signer count below 8, or disable CoC for the template |
| Stakeholder Role dropdown only shows "Signer" | Academy verbatim ("For now we just have the option to select Signers") — other roles are not selectable in the package version tested | Check current package version for additional roles |
| Qes signature method missing a sub-option (e.g. iDIN) | Not enabled on the tenant — each QES method typically requires a separate licence / integration | Contact `support@pdfbutler.com` |
| Email body shows raw `[[!SignButler.SignURL!]]` | Using a Classic email template (not Lightning) or template not stored in / shared from `SignButlerEmails` | Convert to Lightning Email Template in `SignButlerEmails` |

## Verify in-org — what the Academy does NOT publish

The SIGN Butler V2 Academy is UI-focused; several API-level identifiers are not spelled out on the 10 public pages. Before quoting these, verify in the target org:

1. **Object API names** — tabs show `Sign requests`, `Sign request templates`, `Brandings` (plus Audit Trail referenced in CoC). Likely `cadmus_sign2__SignRequest__c`, `cadmus_sign2__SignRequestTemplate__c`, `cadmus_sign2__Stakeholder__c` (or `...Signer__c`), `cadmus_sign2__Branding__c`, `cadmus_sign2__AuditTrail__c` — **not confirmed**.
2. **Custom field API names** — every template / stakeholder / branding label is published by display label only.
3. **Sign Request Status picklist values** — Academy does not publish a canonical status list. Email template stems (`Created`, `Reminder`, `Download`, `Expired`, `MailOtp`) suggest statuses but are template name suffixes, not confirmed picklist values.
4. **Batch / Schedulable class names** — three jobs (Reminder / Warning / Expiry) documented conceptually; no Apex class name published. Check Setup → Apex Jobs after first run.
5. **CoC toggle field** — "can be enabled on the SIGN Request Template" without naming the field.
6. **Branding object fields** — logo / header colour / button colour referenced; schema not published.
7. **Stakeholder roles** beyond `Signer` (Approver, Receiver, Filler, Witness signer) are marketing-facing only as of the config PDF vintage.
8. **Signature-method sub-options** for `Qes` — iDIN / ItsMe / A Trust / Belgian eID-card are named in prose but not mapped to picklist values.
9. **Static Resource full asset list** (`SIG001TOSIG010`) — only `SIG001.png` and `SIG002.png` confirmed in writing.
10. **"extra email merge fields datasource" schema** — likely KEYVALUE, not published.
11. **Connected App / Named Credential names** — registration goes via the Admin tab UI; the underlying Connected App (labelled "SIGN Butler Connected" on consent) is not exposed by Name in the Academy.
12. **CoC storage field** — where on the Sign Request the sealed CoC PDF lands (likely Files related to the record) is not spelled out.

For each of the above, query the installed org directly — do NOT invent identifiers.
